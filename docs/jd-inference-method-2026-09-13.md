## 一、方法说明

### 1.1 方法链条

```
公开招聘 JD（Fact）
  → 岗位职责 / 工作内容（Fact — 公开来源明确列出）
  → 客户正在用"人+手工"解决什么问题（Inference — 从职责反推）
  → 手动、重复、可数字化的环节（Inference）
  → 对应 iMS + Instrument 切入场景（Inference — 需再次验证）
```

### 1.2 证据纪律（与 Radar 全局规范一致）

- JD 文本本身 = **Fact**（来源 URL 可查证）
- 从"岗位职责存在"推导"客户存在相应人工工作负载" = **Inference**（职责存在是事实，工作量/痛点强度是推断）
- 从"人工工作负载存在"推导"客户要买 iMS" = **Inference**（需求强度、预算、决策链完全未知）
- 未检索到专岗 JD 的线索 = 标 **UNKNOWN / LOW**，不允许用行业常识强行推断

### 1.3 三条过滤规则

1. **有岗位、无职责细节**：只记录岗位存在（Fact），不做需求推断。
2. **有职责、无数字/软件要素**：若职责全部为离线操作（如"电焊/管道安装"），不得推断数字化需求。
3. **职责含"记录/报表/台账/统计/巡检/数据/合规填报"等要素**：才是软件需求推断的候选证据。

## 三、核心洞察

### 3.1 REPEATABLE DEMAND SIGNAL（本轮最重要发现）

**楚能集团三基地（襄阳/宜昌/孝感）出现完全同构的需求模式**：

- 襄阳基地：环保体系工程师（排污证后管理 + 污水站达标排放）+ 污水处理工程师（台账报表）
- 宜昌基地：环保工程师（废水站运行管理 + 排污证后管理）— **职责与襄阳同构**
- 孝感二期：动力设备技术员（水系统运维记录）

→ 同一集团、多个基地、相同岗位职责、相同的手工台账/证后管理痛点。
→ **标记为 REPEATABLE DEMAND SIGNAL：锂电池集团多基地水系统运维与合规记录数字化。**

### 3.2 细分模式：合规报告自动化（亿纬锂能最扎实）

亿纬锂能 JD 是**全库证据强度最高的单条 JD**：环保助理工程师直接写"废水站运营管理、日常数据汇总、月度运营报告"，环保工程师写"排污许可执行年报/环统/依法披露/ESG 填报"。
→ 明确暴露人工收集+编制报告的重复性工作负载，这是 iMS 可验证的 Demand 而非 Feature。

### 3.3 细分模式：半导体厂务仪表维护与巡检数字化

中芯国际（集团多厂区）+ SK海力士大连均招聘厂务水处理/给排水岗位，且中芯 JD 明确含"仪表维护和巡检、系统风险评估"。
→ 半导体厂务水系统仪表健康管理与巡检数字化是跨客户复现的需求模式（REPEATABLE）。

### 3.4 对 iMS GTM 的启示

1. **话术从"我们能做 X"改为"我们知道你怎么统计废水站数据的"**：JD 提供了客户内部真实工作语言的词汇表（台账、排污年月报、环统、ESG 填报、周报 Excel）。
2. **集团 ROI 论证优先楚能、亿纬、中芯这类多基地客户**：同一岗位职责跨基地复现 = 标准化部署 + 集团采购潜力。
3. **合规报告时间线是天然 PULL 触发点**：排污许可年报、环统填报等有硬性截止日期，是 Unavoidable 的强候选。

3. **双鹤沧州**：使用集团内其他基地（商丘）的 JD 作参照，属 Inference，需沧州本地验证。
4. **JD 推断的能力边界**：JD 证明"岗位职责存在"与"存在人工工作负载"，**不证明**客户已打算采购软件、有预算、当前方案确实失效。这些仍需 PULL Qualification 的 U/L 维度验证。
5. **MD 中标注的 HIGH 指 JD 证据质量**，不等于 PULL Score / 销售优先级。
