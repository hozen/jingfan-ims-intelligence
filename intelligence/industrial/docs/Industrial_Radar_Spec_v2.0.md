# iMS Industrial Opportunity Radar Daily
# 工业机会雷达 Stage 1 + Stage 2 完整改进规格

请更新现有的 **iMS Industrial Opportunity Radar Daily / iMS 工业机会雷达日报** 周期任务。

这不是一次性修改 2026-09-08 的 PDF。

**必须修改周期任务本身，使今后每次工业雷达运行都遵循以下逻辑。**

---

# 0. 强制语言要求

## 最终报告必须使用简体中文

这是面向 Hach China 内部团队阅读、决策和分享的工业机会雷达。

因此：

- PDF 正文必须使用简体中文。
- 首页、线索卡片、Qualification 结论、市场洞察、下一步行动均必须使用中文。
- 不生成英文版。
- 不需要中英双语重复。
- 专业缩写可以保留英文，例如：
  - iMS
  - Hach
  - EPC
  - ZLD
  - DCS
  - EHS
  - PASS / WATCH / REJECT
- 公司、项目、法规优先使用官方中文名称。
- 来源标题如果原文为英文，可以保留英文。
- 内部机器读取字段可以保留英文 key，但呈现给人的 PDF 必须以中文为主。

PDF 中字段名称优先显示为：

- Why This Matters → 为什么值得关注
- Recommended Next Action → 建议下一步
- Missing Evidence → 缺失证据
- Upgrade Condition → 升级为 PASS 的条件
- Downgrade Condition → 降级为 REJECT 的条件
- Entry Window → 介入窗口
- Qualification Confidence → 资格判断置信度
- Market Insight → 市场洞察
- Relevant Package → 相关水务/仪表包
- Project Stage → 项目阶段
- Hach Fit → Hach 匹配度
- iMS Fit → iMS 匹配度

目标：

> 中国区销售、Vertical Manager 和管理层拿到 PDF 后可以直接阅读和转发，不需要翻译。

# 1. 首先纠正这份报告的任务定义

最近一次报告的问题主要不是 PDF 排版。

**不要因为本次修改而退回旧版 PDF 视觉设计。**

当前新版布局框架可以继续使用和优化。

真正的问题是：

> 报告从“Stage 1 Discovery + Stage 2 Qualification”
> 退化成了“搜索结果 / 招标信息 / 新闻摘要”。

必须纠正。

这份报告不是：

- 环保新闻摘要；
- 行业新闻摘要；
- 招投标信息列表；
- 政策新闻列表；
- “可能存在 iMS 场景”的项目集合；
- 搜索 Agent 尚未解决的问题清单；
- 把大量“待验证”问题交给读者的研究中间稿。

它是：

# Stage 1 Discovery + Stage 2 Qualification 的正式输出

核心问题只有一个：

> 今天发现的这些信号中，哪些已经构成值得 Hach / iMS 继续投入资源的真实销售机会？

最终必须帮助读者做出：

**PASS → WATCH → REJECT**

的资源配置判断。

保持以下五阶段定义：

## Stage 1 — Discovery / 发现

- 项目
- 招标
- 环评
- 扩产

- 政策变化
- 监管变化
- 设备升级
- 数字化改造
- 其他可能产生 Hach / iMS 机会的 Public Trigger

↓

- 时间线
- 水/环保场景
- Relevant Package
- Hach Fit
- iMS Fit
- Procurement / Entry Window
- Why Now
- Missing Evidence
- PASS / WATCH / REJECT
- 下一步行动

↓

## Stage 3 — Enrichment / 丰富

只针对值得继续投入资源的线索：

- 找项目链组织
- 找设计院

- 找关键联系人
- 找联系方式
- 找影响采购的角色

↓

## Stage 4 — Outreach / 触达

- 业主

- 环保负责人
- 公辅负责人
- 其他关键角色

↓

## Stage 5 — Orchestration / 编排

持续：

- 推进
- 分配资源
- 跟踪项目变化
- 记录反馈
- 更新 Opportunity
- 驱动下一步动作

在首页明确高亮：

> **本日报当前负责 Stage 1 Discovery + Stage 2 Qualification。**

Stage 3 不应重新替 Stage 2 做 Qualification。

Stage 3 应当直接消费已经 Qualification 完成的 PASS，以及少数明确指定进入 Enrichment 的 WATCH。

# 3. Stage 2 必须真正完成 Qualification

Stage 2 的工作不是：

> 找到一个项目，然后列出三个“待验证问题”。

Stage 2 必须主动研究这些问题，并尽可能在报告发布前解决。

只有真正无法通过公开资料解决、且会影响商业判断的关键问题，才允许进入 Missing Evidence。

# 4. 每条线索必须完成以下 Qualification

## A. 项目主体 / Entity Verification

确认：

- 准确客户主体是谁？
- 项目业主是谁？
- 项目是否真实存在？
- 是否能够独立验证？
- 当前项目阶段是什么？
- 最新时间线是什么？
- 信息是否仍然 Fresh？
- 是否存在同名项目？
- Stage 1 是否混入了两个不同项目？
- Stage 1 的投资额、地点、产能、项目阶段是否有错误？

如果 Stage 1 错了：

**明确纠正。**

如果一条线索实际上包含两个项目：

**拆分。**

如果主体无法确认：

**返回 Stage 1 修正，而不是继续假装 Qualification。**

# 5. 验证真实的 Water / Environmental Opportunity

不要看到：

> 化工厂 / 电池厂 / 电厂

就自动推断存在 iMS Opportunity。

必须研究：

### 是否真的存在相关水系统？

例如：

- 工业废水
- 污水处理
- ZLD
- 循环水
- 冷却水
- 锅炉水
- 蒸汽系统
- RO
- 除盐水
- 超纯水
- 工艺水
- 回用水
- 环境监测
- 排口监测
- 在线水质分析
- 水质仪表
- 仪表联网
- 数据质量管理

并判断：

### Water Signal 强度

使用：

- Confirmed
- Strongly Inferred
- Possible
- No Evidence

不要把 Possible 写成事实。

---

# 6. 判断 Water System Ownership

这是 Qualification 的重要部分。

必须尽可能判断：

- A — 客户自建自营
- B — 园区集中处理
- C — 第三方运营
- D — EPC / Package Vendor 控制
- Unknown — 无法确认

因为：

> 有水处理需求 ≠ 客户自己拥有采购权。

如果客户只是把废水排入园区集中污水厂：

可能存在工厂端监测需求，

但不应把园区污水处理系统自动算成客户自己的 Opportunity。

# 7. Hach Fit 和 iMS Fit 必须分开判断

这是本次修改最重要的要求之一。

## Hach Fit

回答：

> 这个项目是否真实存在 Hach 仪表 / 分析仪 / 水质监测机会？

例如：

- 在线分析仪
- 水质仪表
- 环境监测
- 排放监测
- 工艺监测
- 实验室 / 在线组合
- 相关 Hach 产品

---

## iMS Fit

单独回答：

> 为什么这个客户需要 iMS，而不仅仅需要几台仪表？

寻找真正的 iMS Trigger：

例如：

- 多仪表
- 多品牌仪表
- 多站点
- 大量 Installed Base
- 仪表生命周期管理
- 维护困难
- 数据质量问题
- 设备状态不可见
- 多系统数据孤岛
- DCS / SCADA / 平台集成
- 合规报告
- 监管数据联网
- 多排口管理
- 多厂统一管理
- 远程运维
- 预测性维护
- 大规模仪表资产管理

---

iMS Fit 可以是：

- Strong
- Medium
- Weak
- No Evidence

**No Evidence 是允许且必要的判断。**

禁止因为项目里出现“仪表”就自动写：

> “iMS 可以用于监测、告警、合规管理。”

这类没有客户级证据支持的通用产品描述必须删除。

# 8. Relevant Package 必须明确

每条值得追踪的项目尽量识别：

> Hach / iMS 到底进入哪个 Package？

例如：

- 污水处理包
- ZLD Package
- 循环水
- 除盐水
- 超纯水
- Boiler Water
- Environmental Monitoring
- Online Analyzer
- Instrumentation
- Automation
- Utilities
- EPC Water Package

不能只说：

> “这个项目有水处理需求。”

必须尽量定位到真实采购包。

---

# 9. Entry Window / Procurement Window 是核心判断

每条线索必须回答：

> 我们现在进入还来得及吗？

统一使用：

- EARLY
- GOOD
- LATE
- CLOSED
- UNKNOWN

研究 Relevant Package 当前阶段：

例如：

- Planning
- Feasibility
- EIA
- Basic Engineering
- Detailed Design
- EPC Tender
- EPC Awarded
- Equipment Procurement
- Installation
- Commissioning
- Operating

注意：

> 大项目 ≠ 好机会。

如果已经采购结束：

即使是几十亿、几百亿项目，也可能 REJECT。

反过来：

一个规模较小但刚进入 Basic Design、仪表规格尚未冻结的项目，可能更加值得 PASS。

# 10. PASS / WATCH / REJECT 必须成为真实决策

不要把 WATCH 当成安全默认值。

---

## PASS

PASS 的含义：

> 已有足够证据证明这是一个值得投入 Stage 3 资源的真实商业机会。

通常至少应有：

- 主体可确认；
- 项目真实；
- 时间线可信；
- Relevant Water / Environmental Package 可识别；
- Hach Fit 有依据；
- iMS Fit 有依据，或者存在明确且重要的 Hach instrumentation opportunity；
- Entry Window 可用。

PASS 后必须明确：

### 建议下一步

**进入 Stage 3 Enrichment**

并说明 Stage 3 应该找谁。

例如：

- 业主工程负责人
- 公辅负责人
- 环保负责人
- 仪表自动化负责人
- EHS
- 设计院
- EPC
- 水处理 Package Vendor

---

## WATCH

WATCH 只能用于：

> 存在明确潜力，但一个或少数几个关键 Gating Fact 尚未解决。

每个 WATCH 必须包含：

### 缺失证据

到底缺什么？

### 升级为 PASS 的条件

发现什么证据后可以升级？

### 降级为 REJECT 的条件

发现什么证据后应该停止？

### Agent 下一步研究动作

Agent 接下来具体查什么？

不要简单写：

> 待验证：
> - 是否有 Hach？
> - 是否有在线仪表？
> - EPC 怎么采购？

然后把研究任务交给读者。

这些问题首先应该由 Stage 2 Agent 自己尝试解决。

---

## REJECT

不要害怕 REJECT。

以下情况应积极考虑 REJECT：

- 第三方检测服务，并非设备 / iMS Opportunity；
- 项目已经采购完成；
- Entry Window 已关闭；
- Relevant Package 与 Hach 无关；
- 没有真实水系统；
- 客户没有水系统 Ownership；
- 只有泛化政策关联；
- 只有行业理论需求，没有客户证据；
- iMS Fit = No Evidence 且 Hach Fit 也弱；
- 主体无法验证；
- 项目信息错误；
- 重复线索且没有新信息；
- 纯新闻；
- 泛化设备采购；
- 与 iMS GTM 无明确关系。

Radar 的价值不仅是：

> 找机会。

也包括：

> **快速消灭噪音。**

---

# 11. 政策 / 法规变化不能直接当成客户 Opportunity

例如：

> “生态环境法规变化导致重点排污单位需要自动监测升级”

这是非常重要的 Market Trigger。

但：

> “全国所有重点排污单位”

不是一个销售 Account。

因此必须把这类内容放入单独模块：

# 市场 / 监管 Trigger

每个重大 Trigger 回答：

### 发生了什么变化？

### 为什么会产生商业影响？

### 哪些行业最受影响？

### 可能产生什么 Hach Opportunity？

### 可能产生什么 iMS Opportunity？

### 下一步 Stage 1 应该搜索哪些具体 Account？

例如：

> 不要停留在“所有重点排污单位”。

下一步应该变成：

> 找出具体省市已经开始执行的名单 →
> 找出具体重点排污企业 →
> 判断哪些企业需要新增 / 升级自动监测 →
> 形成真正 IND Lead。

只有出现：

**具体企业 / 具体厂区 / 具体项目**

之后，才进入正常 Opportunity Qualification。

---

# 12. 首页必须改成真正的 GTM 决策页

不要让管理者读完十几页才看到 Insight。

## Page 1 — 今日 GTM 摘要

要求：

> 60 秒内可以读完。

---

## A. 今日最值得关注的机会

最多：

**3–5 条。**

每条只显示：

**Lead ID | 客户/项目 | 为什么值得关注 | 判断 | 介入窗口 | 下一步**

例如：

> IND-XXXX  
> XX 化工新建污水系统  
> 污水 Package 已确认，Basic Design 阶段，Hach Fit Strong / iMS Fit Medium  
> **PASS | EARLY**  
> 下一步：Stage 3 找业主公辅 + EPC 仪表负责人

---

## B. 今日市场洞察

只写：

**1–3 条真正的跨线索 Insight。**

例如：

> 火电和电池项目连续出现 ZLD，但多数仪表采购权位于 EPC，因此当前 GTM 的关键可能不是直接找 Owner，而是建立 ZLD EPC 影响路径。

这叫 Insight。

不要写：

> “今天发现 3 个火电项目、2 个化工项目。”

那只是统计。

## C. 与上一期相比发生了什么？

只报告有意义的 Delta：

- 新 PASS
- PASS → WATCH
- WATCH → PASS
- WATCH → REJECT
- 新证据
- Entry Window 改变
- Entity 修正
- 新的行业模式
- 新的 Regulatory Trigger

没有变化的旧线索不要占首页。

# 14. 大幅删除低价值文字

请主动压缩报告。

使用下面这个判断：

> 如果删除一句话不会改变：
>
> - PASS / WATCH / REJECT
> - Hach Fit
> - iMS Fit
> - Entry Window
> - Recommended Next Action
>
> 那么强烈考虑删除。

重点删除：

- 泛化行业介绍；
- “大型工厂因此可能有大量废水”之类显而易见推断；
- “环保要求趋严可能产生需求”之类泛化描述；
- 重复项目背景；
- iMS 通用产品能力介绍；
- 没有行动意义的 Unknown；
- 大量“可能 / 预计 / 推断”但无法影响决策的文字；
- 为了填满页面而生成的文字。

目标不是：

> 每条 Lead 必须写满 1–3 页。

而是：

> **值得深入的 Lead 可以 1–3 页；简单 REJECT 可能只需要半页甚至一张小卡片。**

信息密度优先于页数。

# 15. 重复线索必须只报告 Delta

如果某条 Lead 已经在过去日报出现：

不要每天重新写一次完整故事。

必须显示：

**上一状态 → 新证据 → 新状态**

例如：

> WATCH  
> ↓  
> 找到 EPC 中标结果 + Instrument Package 尚未采购  
> ↓  
> PASS

如果没有任何 Material Change：

放入：

# Monitoring / No Material Change

并极度压缩。

甚至可以不进入主报告正文。

Radar 应该奖励：

> **New Information**

而不是：

> **Repeated Information**

---

# 16. 报告最后必须有真正的 Cross-Lead Insight

不要只做：

- 行业数量统计
- 来源数量统计
- PASS 数量统计

这些可以保留，但不是重点。

必须进一步回答：

### 今天的线索共同说明了什么？

例如：

- 某类项目正在集中进入采购窗口？
- ZLD 是否反复出现？
- EPC 是否正在成为关键采购控制点？
- 某项监管政策是否已经从中央政策进入地方执行？
- 某个行业的 iMS Fit 是否明显高于其他行业？
- 新建项目多还是 Installed Base Upgrade 多？
- Direct Owner 机会多还是 EPC Route 多？
- 当前 Radar 是否搜索了太多“有水但没有 iMS”的项目？

最终形成：

# 今日 GTM Insight

它应该是管理者愿意转发的一段内容。

---

# 17. 必须区分“Opportunity”和“Market Insight”

这是非常重要的分类。

### Opportunity

必须有：

> 具体 Account / Project。

### Market Insight

可以来自：

> 多个项目共同形成的模式。

### Regulatory Trigger

可以来自：

> 政策 / 法规变化。

三者不要混在同一个 Lead List 中。

# 19. 发布前执行 Quality Gate

每次生成日报前，必须自检：

## Q1
销售经理只看第一页，是否知道今天最值得做什么？

## Q2
每个 PASS 是否真的值得消耗 Stage 3 资源？

## Q3
每个 WATCH 是否只有明确的 Gating Fact，而不是“研究没做完”？

## Q4
是否明确区分了：

**Hach Instrument Opportunity**

和：

**iMS Software Opportunity？**

## Q5
是否把全国性政策误当成一个客户 Lead？

## Q6
是否出现大量：

> “iMS 可用于监测、告警、数据管理……”

这样的通用套话？

如果有，删除。

## Q7
Stage 2 是否真正完成了 Research + Qualification？

还是只是把问题写成：

> “待验证”？

如果是后者：

继续研究后再发布。

## Q8
是否有重复 Lead？

如果有：

只报告 Delta。

## Q9
是否存在本来应该 REJECT、但为了保守而写成 WATCH 的项目？

重新判断。

## Q10
如果当天：

**PASS = 0**

必须额外进行一次自检：

> 今天真的没有合格机会？

还是：

> Agent 的 Qualification 停得太早，所以所有东西都停留在 WATCH？

不要为了 KPI 人为制造 PASS。

但是也绝对不要默认 WATCH。

# 20. 恢复旧版 Qualification Engine 的判断纪律

请恢复之前 Stage 2 Qualification 的核心能力。

一个好的 Qualification 结果应该类似：

> Water Signal = Confirmed  
> Project Stage = Planning / Pre-Basic  
> Relevant Package = 污水处理 + 在线分析  
> Hach Fit = Strong  
> iMS Fit = Strong  
> Entry Window = EARLY  
> Decision = PASS  
> Recommended Action = 进入 Stage 3，寻找 Owner Engineering / Utilities / Environmental / Design Institute。

或者：

> Water Signal = Confirmed  
> Relevant Package 已采购  
> iMS Fit = No Evidence  
> Entry Window = CLOSED  
> Decision = REJECT。

或者：

> Stage 1 把山东项目与广西项目混成一条 Lead  
> → Stage 2 主动纠错  
> → Split 成 A / B  
> → A REJECT  
> → B PASS。

这才是 Stage 2 的价值。

# 21. 不要为了新版式牺牲研究深度

新版 PDF 可以：

- 更清晰；
- 更漂亮；
- 更适合手机阅读；
- 更卡片化；
- 更容易扫描。

但是：

**视觉简化 ≠ Research 简化。**

后台研究可以很深。

前台呈现应该很短。

原则：

> Deep Research → Strong Qualification → Concise Output

而不是：

> Shallow Research → Long Narrative

# 22. 最终目标

这次修改不是让日报：

> “信息更多”。

而是让它：

> **更值得做销售决策。**

最终目标：

**Less information, more qualification.**

**更少泛化项目，更多真实 Account。**

**更少“待验证”，更多 Agent 已经完成的判断。**

**更少 WATCH-by-default，更强的 PASS / REJECT。**

**更少 iMS 万能套话，更严格地区分 Hach Fit 与 iMS Fit。**

**更少重复信息，更多 Delta。**

**更少项目摘要，更多 GTM Insight。**

最终判断标准非常简单：

> 一个 Hach China Vertical Manager 或 Sales Manager 拿到这份日报，
> 是否能在 60 秒内知道：
>
> 1. 今天发生了什么值得我知道？
> 2. 哪几个客户真的值得追？
> 3. 为什么？
> 4. 现在是不是合适的介入窗口？
> 5. 下一步具体应该做什么？

如果不能做到，就继续修改，不要发布。
